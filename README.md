# FoG Farmer

Асинхронный Telegram-фармер для `@fogmmobot` с отдельной панелью управления.
Игровая сессия работает через Telethon, панель администратора — через aiogram,
состояние и статистика хранятся в SQLite.

Текущие карта, мана и навыки изолированы в сменном legacy-пакете. Границы
модулей, гарантии и порядок подключения будущего поиска по кнопке описаны в
[ARCHITECTURE.md](ARCHITECTURE.md).

## Управление

Откройте /menu в управляющем боте. На экране «Обзор» доступны запуск,
безопасная пауза, продолжение и остановка. План циклов, выбор мобов, лечение
и темп собраны в «Настройках».

При начале передышки между циклами приходит сообщение с кнопкой
«Пропустить передышку». Она сразу запускает следующий цикл; эта же кнопка
и время автоматического продолжения доступны на экране «Обзор».
Кнопка относится только к своей передышке: повторное нажатие или старое
сообщение не пропускает новую передышку и не снимает ручную паузу.
Ожидание, назначенное Telegram, продолжает соблюдаться.

## Основные модули

- `farmer.py` и `supervisor.py` управляют очередью, сессией и остановкой, не
  разбирая правила карты или боя.
- `game_mechanisms.py` задаёт контракт сменного набора игровых механик.
- `legacy_fog_mechanisms.py` собирает текущие map/combat реализации и consumer
  уведомлений о картах; весь пакет заменяется одной фабрикой.
- `event_ingress.py`, `message_snapshot.py` и `telegram_action_executor.py`
  защищают порядок событий и актуальность действий.
- `battle_records.py`, `storage.py` и `battle_outbox.py` ведут обязательный
  транзакционный журнал и задания внешних эффектов.
- `automation_policy.py` и `settings_service.py` публикуют валидированные
  неизменяемые настройки.

## Требования

- Python 3.11+
- Telegram `api_id` и `api_hash`
- токен отдельного управляющего бота
- Telegram ID администратора

## Локальный запуск

```bash
python -m venv .venv
# Linux/macOS: source .venv/bin/activate
# Windows: .venv\Scripts\activate
python -m pip install --require-hashes -r requirements.lock
```

Скопируйте `.env.example` в `.env` и заполните значения. Сам Python не читает
`.env` автоматически: экспортируйте переменные окружения или передайте файл
контейнеру. Для локального хранения задайте `FOG_DATA_DIR` на доступный каталог.

Перед первым запуском авторизуйте игровую Telegram-сессию в интерактивном
терминале. Команда запросит номер телефона, код Telegram и пароль 2FA, если он
включён. Используйте тот же `FOG_DATA_DIR`, что и для приложения.

```bash
python authorize.py
python main.py
```

`main.py` использует уже авторизованную сессию и не запрашивает данные через
панель бота. При сброшенной авторизации повторите `python authorize.py` после
остановки приложения.

Обязательные переменные:

- `TELEGRAM_API_ID`
- `TELEGRAM_API_HASH`
- `CONTROL_BOT_TOKEN`
- `ADMIN_TELEGRAM_ID`

Необязательные: `FOG_DATA_DIR` (по умолчанию `/app/data`) и
`FOG_CHARACTER_NAME` (по умолчанию `Kombat`).

## Docker

```bash
docker build -t fog-farmer .
# Выполните один раз для нового volume или после сброса авторизации:
docker run --rm -it --env-file .env -v fog-farmer-data:/app/data fog-farmer python authorize.py
# Дальнейшие запуски используют ту же сохранённую сессию:
docker run --rm --env-file .env -v fog-farmer-data:/app/data fog-farmer
```

Каталог данных содержит SQLite, Telethon-сессию и журналы. Не добавляйте его в
образ и не публикуйте: файлы сессии дают доступ к Telegram-аккаунту.

## Проверки

```bash
python -m pip install --require-hashes -r requirements-dev.lock
```

## База данных

Схема обновляется при старте и имеет номер в `PRAGMA user_version`. Перед
развёртыванием новой версии остановите процесс и сохраните вместе файлы
`fog_farmer.sqlite3`, `fog_farmer.sqlite3-wal` и `fog_farmer.sqlite3-shm`, если
они существуют. Не копируйте работающую SQLite по одному файлу.

Миграция журнала сохраняет числовые battle id и дочерние записи. Уникальность
исхода основана на стабильном `SourceEventId`; Telegram message id хранится как
неуникальное происхождение и может повторяться в разных боях.

## Гарантии обработки и восстановления

Для каждого входящего события создаётся неизменяемый снимок точного текста,
кнопок, callback bytes и редакции сообщения. Игровые правила читают этот снимок;
Telegram RPC хранится отдельно и не может изменить уже принятые данные.

Входящие игровые события обрабатываются последовательно. Заполнение очереди
приостанавливает приём до освобождения места; принятое событие не подтверждается
до успешной обработки. Устаревшая карта или ход не получают новое действие,
изменение клавиатуры не обучает боевую модель повторно. Callback с неизвестным
результатом доставки не отправляется автоматически ещё раз.

Исход боя, награды и задания общего durable outbox записываются одной
транзакцией. Legacy-пакет владеет consumer-ом нынешних уведомлений о картах; во
время graceful drain он не начинает новые отправки, а после перезапуска продолжает
pending intents. Повреждённое задание изолируется и не блокирует следующие.
Telegram RetryAfter действует на всю namespace и хранится в базе.

Боевые решения выполняются версионированным legacy ruleset, а знания разделены
по версии правил и модели. Повреждённые значения памяти отбрасываются при чтении.
Ошибка необязательной памяти не отменяет записанный исход и не мешает завершить
бой. Неизвестные ключи настроек сохраняются до явной миграции.

Запрос состояния ограничен 10 секундами. Для состояния без ответа повтор разрешён
через 30 секунд и выполняется watchdog с учётом его таймаута. После трёх
безуспешных попыток восстановления фармер останавливается с объяснением причины.
Telegram FLOOD_WAIT сохраняется и соблюдается после перезапуска.

Остановка запрещает новые события и эффекты, дренирует уже принятую очередь,
завершает принадлежащие сессии задачи, закрывает механизм и фиксирует terminal
state. Только Supervisor отключает Telegram и освобождает session lease. Если
фаза очистки завершилась ошибкой или timeout, владелец сохраняется для повторного
`stop/close`, а конкурентный запуск блокируется.

Уведомления имеют семантику at-least-once: авария после отправки и до ACK может
дать повтор. Полностью одинаковые source scope, message id, edit timestamp, текст
и кнопки неразличимы без серверного battle nonce и считаются повторной доставкой.

## Допустимые задержки

Все значения должны быть конечными, неотрицательными; максимум не меньше
минимума. Интервалы сохраняются одной транзакцией.

| Настройка | Максимум |
|---|---:|
| Перемещение, открытие атаки, выбор цели, навык | 300 секунд |
| Короткая пауза | 3600 секунд |
| Передышка между циклами | 1440 минут |

Некорректные старые значения заменяются стандартным диапазоном при загрузке.
В интерфейсе передышка задаётся в минутах, остальные задержки — в секундах.

## Обновление зависимостей

`requirements.txt` и `requirements-dev.txt` задают допустимые прямые зависимости.
Lock-файлы фиксируют весь проверенный набор и хеши пакетов; Docker и CI используют
именно их. Обновляйте оба файла вместе, затем выполняйте тесты и `pip check`.

```bash
python -m pip install pip-tools==7.6.1
python -m piptools compile --generate-hashes --strip-extras --no-emit-index-url --no-emit-trusted-host -o requirements.lock requirements.txt
python -m piptools compile --generate-hashes --strip-extras --no-emit-index-url --no-emit-trusted-host -o requirements-dev.lock requirements-dev.txt
```
